# نصب و بروزرسانی Office از GitHub یا ZIP

نصب اولیه و بروزرسانی ZIP معتبر Office از Central و agent نسخهٔ `1.4.0-rc.14` در دسترس است. برای بروزرسانی، Office موجود باید یک نصب Docker با helper فعال باشد. در این روش ZIP سورس به سرور مشتری می‌رسد؛ برای انتشار کدگذاری‌شده، بستهٔ Docker با encoder را انتخاب کنید.

## ۱. بروزرسانی Central و agent موجود

روی سرور Central:

```bash
cd /opt/office-central
sudo bash centralctl.sh update v1.4.0-rc.15
sudo docker compose exec -T app php artisan office:index-source-releases
sudo bash centralctl.sh doctor
```

فرمان دوم، ZIPهای سورس قبلاً دریافت‌شده را با SHA-256 اصلی و شمارهٔ VERSION بررسی می‌کند و موارد معتبر را برای انتخاب در لایسنس آماده می‌کند. هنگام ارتقا از اسکریپت قدیمی این فرمان را یک بار اجرا کنید؛ اسکریپت جدید در استقرارهای بعدی آن را خودکار اجرا می‌کند و اجرای مجدد آن بی‌ضرر است. فایل اصلی، شناسهٔ نسخه، لایسنس و اطلاعات نصب تغییر نمی‌کنند. سورس فاقد helper یا بستهٔ خراب قابل مجاز کردن نیست؛ علت در خروجی بررسی اعلام می‌شود.

روی هر سرور Office موجود، یک بار agent را تازه کنید:

```bash
curl --fail --proto '=https' --tlsv1.2 https://update.ponet.ir/agent/install.sh -o /tmp/office-helper-install.sh
sudo bash /tmp/office-helper-install.sh
sudo office-agent status
```

برای نصب متصل، همان شناسه و کلیدهای محلی حفظ می‌شوند و کد مصرف‌شده دوباره لازم نیست. این فرمان برای دریافت agent جدید است؛ نسخهٔ برنامهٔ Office را عوض نمی‌کند. اطلاعات helper را حذف نکنید و مجوز جدید نسازید. برای نصب با مسیر سفارشی، همان `--root /path/to/helper` قبلی را به فرمان بدهید.

## ۲. دریافت و اجازهٔ نسخه

1. در **اتصال مخازن**، محصول مربوط به Office را انتخاب و مخزن آن را همگام کنید. از نسخهٔ rc.15 تشخیص Office بر اساس محتوای معتبر بسته نیز انجام می‌شود؛ تغییر شناسهٔ محصول یا ساخت لایسنس دوباره لازم نیست. وجود GitHub Release الزامی نیست؛ تگ SemVer نیز دریافت می‌شود. برای محصول شناسایی‌شدهٔ Office، بستهٔ آمادهٔ Docker پیوست‌شده اولویت دارد؛ در نبود آن ZIP سورس تگ دریافت می‌شود.
2. یا در **نسخه‌ها ← نسخهٔ جدید**، ZIP سورس GitHub را بارگذاری کنید. شمارهٔ نسخهٔ فرم باید دقیقاً با `VERSION` داخل سورس برابر باشد. ZIP دارای `artisan`، `Dockerfile` با target برابر `managed` و provider مربوط به helper پذیرفته می‌شود. ZIPهای دارای محیط محرمانه، دیتابیس، symlink یا مسیر نامعتبر رد می‌شوند.
3. نسخهٔ پیش‌نویس را **منتشر** کنید. سپس در جزئیات لایسنس، قسمت **مجوز بروزرسانی مشتری**، همان نسخهٔ جدیدتر را انتخاب و **ذخیره نسخهٔ مجاز** را بزنید. دریافت مخزن به‌تنهایی اجازهٔ مشتری را تغییر نمی‌دهد.
4. مدیر مشتری در **تنظیمات سامانه ← بروزرسانی سامانه** بررسی را اجرا، نسخه را تأیید و بروزرسانی را شروع کند.

agent، ZIP مجاز را از `update.ponet.ir` با امضای مرکز و SHA-256 بررسی می‌کند. ساخت ایمیج جدید در پوشهٔ موقت و پیش از توقف Office انجام می‌شود. این ساخت به فضای کافی دیسک، Docker BuildKit و دسترسی به مخازن Docker، Composer و npm نیاز دارد. سپس مسیر بکاپ بررسی‌شده، migration و health check قبلی اجرا می‌شود. دیتابیس، engine دیتابیس، فایل‌ها، APP_KEY، رمزهای موجود و شبکهٔ پروکسی حفظ می‌شوند. شکست ساخت به نصب جاری دست نمی‌زند؛ شکست migration مطابق وضعیت maintenance و بکاپ قابل پیگیری است.

برای **نصب روی سرور خالی** نیز ZIP معتبر و منتشرشده قابل انتخاب است: در لایسنس جدید، نوع «نصب روی سرور جدید» و همان نسخه را تعیین کنید. agent جدید برنامه را می‌سازد، سرویس‌های استاندارد Docker را دریافت و نصب می‌کند. دریافت یا ساخت ناموفق مجوز را مصرف نمی‌کند؛ همان نصب با همان شناسه قابل ادامه است. وجود دیتابیس مشتری روی سرور با مسیر اتصال Office موجود مدیریت می‌شود؛ مسیر نصب تازه دیتابیس موجود را پاک نمی‌کند.

## ۳. آپلود و پروکسی

حداکثر فایل در فرم وب **۱ GiB** است. از rc.15 مرورگر فایل را در قطعه‌های **۲۵۶ KiB** ارسال می‌کند. نوار ۰ تا ۱۰۰٪ انتقال واقعی کل فایل را نشان می‌دهد؛ ۱۰۰٪ فقط پایان انتقال است و بررسی و ذخیرهٔ بسته بعد از آن انجام می‌شود. هر قطعهٔ قطع‌شده حداکثر دو بار با همان موقعیت تکرار می‌شود؛ قطعهٔ تکراری فایل را خراب نمی‌کند. اگر اتصال همچنان قطع بود، در **همان صفحه** دوباره «ذخیره» را بزنید تا ارسال از آخرین قطعهٔ تأییدشده ادامه پیدا کند. خطای فرم مانند شمارهٔ نسخه نیز بدون آپلود دوباره قابل اصلاح است. ذخیرهٔ نهایی با همان شناسه دوباره اجرا شود، نسخهٔ تکراری نمی‌سازد.

نشست آپلود به مدیر و مقصد ایجاد/ویرایش وابسته است؛ فایل موقت پس از ذخیره حذف می‌شود و نشست‌های ناتمام بعد از ۲۴ ساعت پاک می‌شوند. برای هر مدیر حداکثر سه بارگذاری ناتمام مجاز است. انتخاب فایل متفاوت در همان صفحه، آپلود قبلی را لغو می‌کند. پس از بستن یا تازه‌سازی صفحه، ابتدا فهرست نسخه‌ها را بررسی کنید؛ اگر نسخه ذخیره نشده است فایل را دوباره انتخاب کنید. قطع کامل اتصال، خرابی پروکسی یا نبود فضای سرور همچنان به بررسی زیرساخت نیاز دارد.

در Nginx Proxy Manager، برای Proxy Host دامنهٔ `scm.ponet.ir` قسمت Advanced را این‌گونه تنظیم کنید:

```nginx
client_max_body_size 1025m;
proxy_read_timeout 1800s;
proxy_send_timeout 1800s;
client_body_timeout 300s;
```

مقدار قبلی `client_max_body_size` را جایگزین کنید؛ یک directive را دوبار درج نکنید. مقصد SCM همچنان `http://office-central-web:80` است. محدودیت‌ها و timeoutهای PHP و Nginx داخلی با این مسیر هماهنگ شده‌اند؛ Central به تنظیمات NPM خارجی دسترسی ندارد.

برای بستهٔ Docker بزرگ‌تر از محدودیت وب، فایل را روی سرور Central کپی کنید و از `php artisan office:import-runtime --help` داخل کانتینر برنامه برای مسیر ورود مستقیم استفاده کنید. خطاهای ۴۱۳، ۴۱۹، ۴۲۹، ۵۰۲/۵۰۴، ZIP نامعتبر و عدم امکان ذخیره به‌صورت پیام قابل پیگیری در فرم نمایش داده می‌شوند.

این تغییر نسخهٔ Office را افزایش نمی‌دهد: برای مثال می‌توانید نسخهٔ منتشرشدهٔ `3.8.25` را برای مشتری دارای `3.8.20` مجاز کنید. نصب واقعی روی سرور مشتری باید با دستورهای بالا و یک بکاپ تأییدشده بررسی شود؛ آزمون‌های خودکار جای آن را نمی‌گیرند.

## ۴. ساختار فایل قابل بارگذاری

برای Office نسخهٔ `3.8.25`، ساده‌ترین فایل **Source code (zip)** همان تگ GitHub دارای helper است. ZIP می‌تواند فایل‌ها را مستقیم در ریشه یا داخل یک پوشه مانند `office-3.8.25/` داشته باشد. شمارهٔ فرم `3.8.25` است؛ پیشوند `v` فقط در تگ/نام ZIP قرار می‌گیرد.

```text
office-3.8.25/
  VERSION                             ← 3.8.25
  artisan
  Dockerfile                          ← دارای FROM production AS managed
  composer.json
  composer.lock
  bootstrap/providers.php             ← ثبت OfficeLicenseServiceProvider
  docker/Caddyfile
  app/Providers/OfficeLicenseServiceProvider.php
  app/، public/، resources/، routes/ و سایر فایل‌های مخزن
```

از پوشهٔ سرور مشتری ZIP تهیه نکنید: فایل‌های `.env`، `.git`، `node_modules`، پوشهٔ ریشهٔ `vendor`، دیتابیس و کلیدهای دستگاه نباید داخل بسته باشند. `.env.example` مجاز است. ZIP کامل همان مخزن و تگِ دارای helper کافی است؛ بستهٔ Docker برای این روش الزام نیست.

پس از ارتقا، فرمان `office:index-source-releases` برای هر ZIP قدیمی وضعیت و علت خطا و در پایان تعداد بررسی‌ها را چاپ می‌کند؛ اگر هیچ مورد جدیدی نداشته باشد نیز پیام مشخص دارد. نسخهٔ نامعتبر به‌زور آماده اعلام نمی‌شود و SHA-256 اصلی، شناسهٔ نسخه و محتوای بسته عوض نمی‌شوند.
